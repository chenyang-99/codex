# 出稿数据契约 · 文案门禁 v2.6

本 Skill 的门禁只是给“已写出且经过编辑申报的稿件”做保真、范围、可见事实边界检查；不替代人审，不核验互联网来源，不替用户定稿/制图/发布。运行环境可选，有可用工具时调用，否则由主编对同一清单逐条核查。

## V2：新稿证据与价值核查

新选题出稿或整篇重写，先提交研究记录：目标问题、原始来源及其支持的事实、材料间分歧、归纳结论与未知项，再动笔写作。每稿检查诚实吸引力、传播理由、至少一项明确兑现的主导读者回报及通俗准确的表达。收藏、学习、认知、决策、情绪、审美娱乐、信息、实用、身份表达等按类型任选其一或组合，不强制收藏和学习同时存在，也不强制至少两项。只改标题、审稿、保真轻改只核查受影响的事实，不强制整篇重新研究。

研究记录与五价值检查不能证明内容准确或一定传播；工具测试通过不等于人工审校通过、用户定稿或实际发布。


## V2.1 新稿 value_delivery 申报结构

与选题系统 v1.2 保持一致。仅审查字段是否存在且类型属于允许集合，不代表这些价值已经被真正验证：

```json
{
  "value_delivery": {
    "hook": "开头如何引起目标读者注意",
    "shareability": "明确哪类人为何愿意传播；如无实有热度须标编辑预测",
    "primary_payoff_type": "emotion",
    "primary_payoff": "文章让在AI学习焦虑中的读者产生被理解的感受",
    "readability": "用自然口语表达，不编造个案",
    "secondary_payoffs": []
  }
}
```

允许的 `primary_payoff_type`：`utility`、`learning`、`save`、`insight`、`decision`、`information`、`emotion`、`entertainment`、`social_expression`。`secondary_payoffs` 允许缺省或为空，不因缺少第二种回报被拒；`save` 指可反复使用的资料交付，不是“喊观众收藏”。`hook`、`shareability`、`readability` 是编辑说明字段，不是三项额外读者回报。工具不能判断传播分数或文章是否真正令人感动。

## 用户可见价值说明（出稿v2.2，交付格式必备）

所有新稿和结构性改稿须在**可直接复制发布的正文以外**附一份简短价值说明，不能只把内部 JSON 交给用户，也不能把说明掺进正文：

- 主导价值：类型＋稿件中真正兑现的句子/段落/材料。
- 附加价值：零项或多项，逐项说明正文的具体支持；不要虚构。
- 吸引力：具体哪一句开头对谁构成看点。
- 传播潜力：哪类读者、什么分享动机、何种证据等级；尚无平台反馈一律称主编预测。
- 状态：必要时写未实测、未审定、未发布。

机械门禁目前只能确认 value_delivery 的内容声明，不会检查最终聊天是否确实向用户展示了价值说明。**交付层由主编人工逐稿验收**；不可将机器结构检查伪称为稿件已经通过最终交付检查。

## 人工回归案例：一次技术科普从V3到V6.2的六次纠偏（2026-10-19）

此案例来自用户真实的逐轮文字反馈，**只证明用户审稿偏好与内容修改方向**；没有平台发布、阅读或互动数据，不可称为传播效果验证。不复制当次客服题材作为未来稿件模板。

| 审稿阶段 | 真实反馈/症状 | 今后必须检查的可复用问题 |
|---|---|---|
| V3 | 解释Prompt/RAG/微调，却没教怎么用 | 凡承诺“如何使用”，是否提供可执行的第一步、所需材料和成功验证？ |
| V4 | 贴满Python代码，零基础读者难理解 | 是否按照受众能力分层？能否先用自然语言完成合理的最低门槛操作？ |
| V5 | 可复制任务多，核心知识密度又太低 | 是否讲清机制、与相邻方法的区别、为何有效和失效边界，而非只有任务模板？ |
| V6 | 技术知识密度改善，开头却先讲缺乏吸引力的退款政策 | 首屏是否让受众立刻辨认主题与回报？示意场景是否只是为了“具体”而抢位置？ |
| V6.1 | “你一直用错方法”等制造悬念的开头仍被否决 | 对比较型、知识梳理内容，用户要求直说时是否直接点主题，避免擅加焦虑、反转或未经验证的普遍断言？ |
| V6.2 | 用户表示“目前基本上可以定稿” | 这属于**接近定稿的明确正向审稿反馈**，不可据此宣称已发布、已经验证爆款；仅保留必要的最后校对。 |

**稿件质量四轴（人工，不新增机器字段）：**
- **主题与首屏匹配**：读者能否在第一条识别主题与实质收获？标题、开头、正文能否兑现同一承诺？用户偏好不被“通用钩子模板”覆盖。
- **认知增量**：每个核心方法是否有准确机制与至少一个真正有帮助的新认知；前两帖和相邻帖是否重复？“概念多≠知识深，复制多≠学会了”。
- **行动闭环**：用什么工具/材料、复制什么、成功应看到什么、错在哪里、成本/权限是什么；普通聊天与具备执行环境的代理严格区分。
- **目标受众适配**：技术准确性和零基础可理解性同时成立；术语在首次使用时解释；专业文章可有代码，入门文章用分层而非删原理。

**反向测试**：用四个虚构后续任务检验系统是否会泛化出错：
1. 用户要求“直接科普5种AI工具的差别”——应先题名及比较收益，不开篇强插小众企业客服场景或“你肯定做错了”。
2. 用户要求“开发者手把手部署RAG”——应保留正确的代码、环境及运行验收，不因入门科普经验禁止代码。
3. 用户仅说“把第一句改短”——只改开头，第二条至结尾不得擅自重写；已经认可的段落不可因首屏问题被推倒。
4. 用户要求一篇纯AI视觉作品集——不能强迫四层技术机制、教程、Prompt、评测和“学会使用”流程。

机器质量门禁暂不会执行上述语义评分，也不会核对段落是否让真人真正学会；这些属于主编人工验收，需实际用户后续反馈验证是否改进。

## 人工回归样本：Izumi 项目发现型 X 单帖（2026-10-21）

**证据与状态**：用户提供 Izumi 改稿，并要求将改稿方式变成可复用的出稿规则。用户认可精简方向，不代表该稿已发、产生流量、获得样片重传许可。保留“另一个 X 工具价值型长帖 V3”并列路线，不把任何单一范式强制成所有工具稿的格式。

| 前一稿/编辑惯性 | 用户此次改稿体现的选择 | 后续检验问题 |
|---|---|---|
| 铺垫“我发现一组有意思的案例”，详细展开某个香薰蜡烛的广告设定 | 先说 Izumi 项目是什么、有何新意 | 开头一屏内是否出现项目名与核心看点，而非空泛悬念？ |
| 将某一段官方样片/商品需求当成正文主轴，并延伸到自制预算实验 | 现成多个案例一笔带过，聚焦 AI Director 工作方式 | 案例是否服务核心判断，还是抢走读者主要注意力？ |
| 对模型整合、导演与全流程能力换词重复 | 模型组合一段 + Director 如何分镜和组织生成一段 | 这两段各自给出了不同的新信息吗？ |
| 风格模板腔和强行 CTA | 自然的第一人称判断，加一个直达仓库链接 | 是否能删掉“震撼”“彻底改变”“建议收藏”等无内容包装？ |
| 把外部开源示例变成“我做了/我测过”或默认附完整视频 | 明确是官方仓库案例，不声称自行实测 | 外部演示与本人实测是否严格分层？样片转载许可是否单独核实？ |

**正向人工回归**：对“某开源视频制作项目有官方广告案例，请直接写 X 推文”产出一条独立可读的自然段落单帖：项目定位与具体变化 → 必要的模型/制作机制 → 可核官方案例 → 有边界的个人观点 → 官方链接。不得凭空填用户使用经历；没有必要不要求 API 调用实测或逐秒核价，研究证据可在后台完成，不堆进正文。

**反向人工回归**：
1. “帮我核算一条广告的完整 API 账单” → 仍要提供有来源的计价与成本边界，不得因为 Izumi 风格而省略核心数据。
2. “写一篇完整分镜教程/我亲自实测的视频” → 仍须操作条件、实操步骤、素材许可及真实结果，不能套用简短发现帖替代交付。
3. “仅审阅我的原稿/只改一句话” → 保留用户原文结构，不借此次经验擅自重写或删减。
4. “官方仓库开源且贴了广告视频，帮我重新上传完整视频” → 不以 Apache 2.0 代码许可推定附件可自由重传；必要时要求授权或改为官方原链接。
5. “只做短观点/视觉分享” → 不强制植入 AI Director、模型清单、案例枚举、GitHub 链接或固定六段式。

该样本目前属于**人工语义回归要求**，未新增可以客观评价文风的自动算法。GitHub 文件写入和代码测试不等于用户以后的真实满意度与传播效果。

## 输入 JSON

```json
{
  "cases": [{
    "case_id": "demo-1",
    "edit_scope": "minimal",
    "platform": "xiaohongshu",
    "content_type": "tutorial",
    "audience": "有线上课程却一直没学完的人",
    "central_claim": "尝试把AI作为课程整理和复习助手",
    "headline_original": "原文标题",
    "headline_new": "原文标题",
    "original": "用户原文全文（不能补编）",
    "draft": "本次实际修订后的全文",
    "protected_phrases": ["用户要求完整保留的昵称", "用户原文中的真实动作", "用户原文中的幽默收尾"],
    "required_terms": ["用户明确要求写出的功能或关键术语"],
    "proof_plan": "哪些来源或本人操作可证明说法",
    "claims": [
      {"text": "用户真的做过的一次短视频分析", "evidence_status": "user_verified", "presented_as_tested": true},
      {"text": "尚未做完整验证的长课程学习", "evidence_status": "proposed", "presented_as_tested": false}
    ]
  }]
}
```

- edit_scope: `new_draft` / `review_only` / `title_only` / `opening_only` / `ending_only` / `minimal` / `substantive_rewrite`。review_only/title_only 不能修改正文；段落局部修改需要人工检查范围。
- evidence_status: `user_verified` 仅用户实际做过且提供足够明确的说明；`original_source`=已核原文；`third_party_claim`=外部作者声称；`proposed`=设想或准备测试；`unknown`=未知。
- 申报项目越真实越有用。**规则工具无法识别漏填了某项事实**。最终审核仍须人工对照项目总控、用户图片与文字、产品来源；本仓库不会保存私人稿件/用户敏感细节。
- `protected_phrases` 为编辑显式选择的代表性词句，不能当作只保护这些字、其他段落可以删。
- 实际修改超出用户授权，应先交代问题并请用户同意；事实错误优先修复。
- `requires_editorial_review` 不是 `pass` / `publishable`；不能把机器告警数量当真人感评分或成果预测。自动脚本只读取 JSON，输出 `copy-preflight-report.json`。
- 编辑无权将报告中的 `published=false` 改成 true；只有用户确认实际平台发布的作品 URL 或可靠回执才能更新运营台账。

## 必做回归任务

人工历史审稿特别检查四类问题：普通职场不能被程序员案例偷换；不使用AI的普通读者不能被评价；短图文必须提供超出空泛态度的内容；真实“安装夸克Skill并分析2分钟视频”不得被扩大成整套课程实测。豆包V4用户原文的昵称、可复制学习指令、操作过程与末尾玩笑必须保留，除非用户明确要求重写。

## 效果评价

合成单测只是**代码规则的通过率**，不是写作技术比较或平台转化验证。以后收集“已批准题目从零写”和“用户带初稿修稿”的实际样本，人工在不知分组的条件下看事实、意图保留、作者声音、具体增量以及每稿改动次数。原12案例36样稿是同模型同上下文的模拟压力测试，不能当独立A/B。之后只有用户审稿及真实发布表现可支持是否达到项目目标。
